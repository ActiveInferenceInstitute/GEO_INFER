# GEO-INFER 0.4.0 candidate verification

This work prepares a main-branch candidate. It does not publish a tag or wheels.
The implementation preserves the legacy-sweep ancestry beginning at
`cbe6b9c59975254487452d697c2ea961a19f2286`; the hosted main baseline was
`510f1008e698b45aedc4306d65caf898da6cda04`. Changes are prepared on
`codex/0.4-readiness` before a non-forced main integration.

## Stages and acceptance

| Stage | Implemented contract | Evidence required for acceptance |
| --- | --- | --- |
| Execution infrastructure | Shared discovery, selection, process deadlines, immutable attempts and receipts; explicit backend and manuscript profiles | Real missing/stale/malformed/truncated JUnit, empty-lane, interruption and descendant regressions; full inventory reconciliation |
| SPACE/TIME composition | Explicit aware UTC, strict model axes, H3 state identity/order, bounded owned alignment and distinct missing/zero values | Offset/DST-fold and invalid-axis cases; real DATA → SPACE → TIME and BAYES/ACT numerical oracles; seven-cell and pentagon topology |
| Connected runtime and security | DATA transport and backend boundaries; IOT coordinates/timestamps; ART registry-only persistence; exact LOG MILP; independent ACT grid scoring; native SPM; OPS lifecycle | Actual backend behavior, hostile-file atomic rejection, coordinate oracle and exact-port reopening; fresh independent review |
| Packaging and documentation | PLACE-owned Cascadia, separate extras, virtual workspace, executable examples, version parity, generated signposts | All 45 installed wheels outside the checkout, independently installed operation profiles, maintained-page execution, strict packaging/documentation checks |
| Release preparation | Uniform 0.4.0 metadata, intentional lock, migrations, reproducible manuscript, main integration | Clean candidate receipts, source/artifact hashes, full category/H3/coverage gates and exact-commit hosted Python 3.11/3.12 checks |

Each attempt retains its own receipt, stdout, stderr and applicable JUnit under
`.geo-infer-test-results/runs/`. Local preparation diagnostics are retained under
ignored `output/0.4-readiness/`; failed and timed-out attempts remain evidence,
and a later passing attempt does not erase them. CI uploads validation, category,
coverage, wheel and paired-interchange evidence with the candidate revision.

The focused implementation ancestry records execution infrastructure at
`8d57a20247f98e2e12b31d32711b90406f62edcd`, SPACE/TIME at
`f9148ab1f13bdf5559022cd323246a41d53a3e81`, and connected runtime/security at
`bc3d8ef654d3dbfea769de58511afbb2ae578570`. Later review corrections and packaging
commits remain descendants of these stages. Receipts include the complete dirty
source inventory when a preparation attempt precedes the final clean candidate.

The first broad preparation sweeps executed 9,402 unit and 1,240 integration
cases but failed; those attempts are diagnostic evidence, not release acceptance.
Repairs include actual solver and backend failures, incomplete test evidence,
process cleanup, and invalid composition assertions. Independent review uses
real child processes, hostile ART files, numerical oracles, installed optional
dependency boundaries and portable artifact hashes. Its disposition remains
separate from whole-fleet and hosted acceptance.

## Evidence boundaries

Focused module tests and installed-wheel operations establish their recorded
behavior only. Local Python 3.12 acceptance cannot stand in for hosted Python
3.11/3.12 acceptance. A count of discovered files cannot stand in for executed
tests. Missing reports, incomplete execution and failed validators must remain
failures. Whole-repository readiness requires every required gate on the exact
candidate, including paired GNN interchange and both installed-wheel matrix legs.

The subprocess harness controls descendants that inherit the launch environment;
it does not provide a sandbox for deliberately hostile processes that erase
ownership. Actual Windows descendant behavior requires the Windows acceptance
job; POSIX tests do not establish that claim.

CPU CI makes no passing claim for hardware acceleration, licensed datasets,
historical PROJ causality, or advisor authentication. Those remain separate
acceptance items. External service client construction does not establish a live
PostgreSQL, object-store or Redis deployment. Neural profiles use actual CPU
libraries and local fixtures without downloading pretrained weights.

Migration instructions are in [the 0.4.0 guide](0.4.0_migration.md). The required
commands and CI entrypoints remain in the root agent contract and workflow files.
